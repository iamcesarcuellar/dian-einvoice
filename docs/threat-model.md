# Threat model

**English** · [Español](es/threat-model.md)

This page models the platform as it runs here:

- **The local stack**: a Laravel API, a Vue web app, MySQL, Redis, queue workers and an outbox relay, the DIAN simulator and a local mailbox.
- **The emulated cloud** ([infrastructure.md](infrastructure.md)): the application runs as Lambda functions behind API Gateway, fed by SQS and EventBridge Scheduler, each function with a role of its own. SNS, SQS, S3, SES, DynamoDB, KMS and Secrets Manager run in a local emulator, in place of Redis, the local disk and the local mailbox.

The prod stage adds, as code, a private network and a managed database. Both stages also have the edge: one CloudFront distribution in front of the web app and the API. The edge brings its security headers, a firewall in prod and an origin verifier on API Gateway. Where a mitigation depends on these pieces, this page says so. [limitations.md](limitations.md) lists the known gaps.

## Assets

| Asset | Where it lives | How it is protected |
| --- | --- | --- |
| Each company's signing keys (PKCS#12 and its password) | key_store_entries (local), kms_key_store_entries (emulated cloud) | Locally, encrypted with APP_KEY. In the emulated cloud, AES-256-GCM with a data key per certificate that only the KMS key decrypts, bound to the company and the entry by the encryption context. Never returned by the API. |
| Software PIN and technical keys | dian_settings, number_templates | Encrypted with APP_KEY. Only the last four characters of a technical key are shown. |
| API keys | api_keys | The SHA-256 of a 40-character random secret, compared in constant time. Shown once. |
| Webhook secrets | webhook_subscriptions | Encrypted with APP_KEY. Shown once, on creation and on rotation. |
| Passwords and sessions | users, Redis, DynamoDB | Passwords hashed with bcrypt. Sessions in Redis, or in DynamoDB in the emulated cloud, behind an HttpOnly, SameSite=Lax cookie, Secure in production. |
| Invitation and password reset links | team_invitations, password_reset_tokens | Only a hash of the token is stored. The token travels in the email. |
| Invoices, notes, payments and customer data (names, identification numbers, emails, addresses) | MySQL, document storage (local disk, or the S3 bucket), events in the topic and the queues | Every query is scoped to a company. Only the API serves the files, after authorization. The bucket is private, encrypted and versioned. The topic and the queues are encrypted at rest. |
| Integrity of numbering, documents and balances | MySQL | Row locks, gap-free numbering, signed XML with its SHA-256, and immutable accepted documents |
| APP_KEY, Redis password, simulator admin token | backend/.env. In the emulated cloud, APP_KEY and the credentials of the two database identities are in Secrets Manager. | Never committed. The Redis password and the token are random per checkout. Secrets Manager generates the emulated cloud's APP_KEY, which is never written to a file in the repository. |
| Edge secret | Secrets Manager, and the distribution's configuration, which sends it to API Gateway in X-Origin-Verify | Generated by Secrets Manager, never in a template or a file. The origin verifier compares it in constant time, and the verifier's role reads nothing else. The verifier accepts the current and the previous versions, so the secret rotates without interruption (docs/infrastructure.md). Visible to anyone who may read the distribution's configuration. |
| The alarms' chat webhook address | Secrets Manager (the alerts stack) | Whoever holds it can post to the operators' chat. Empty in prod until the operators set it. Read only by the notifier, whose role reads nothing else. Never logged (docs/observability.md). |
| The power to deploy prod | The delivery stack's deploy role (prod, never deployed) | Assumed only with the OpenID Connect token of a job in this repository's production environment, whose reviewers approve each run. One-hour credentials, no long-lived key. Least privilege on the project's resources, no administrator. The role cannot change its own trust policy, which an administrator deploys (docs/deployment.md). |

## Actors

- An anonymous visitor to the API or the web app
- A signed-in user of another company
- A member with a low role (viewer, member)
- The holder of an API key (read-only or read-write)
- The owner of a webhook endpoint
- Customer data typed into documents (names, notes)
- The DIAN web service, whose responses are trusted only after parsing
- A compromised dependency or CDN

## Trust boundaries

1. **Browser and web app → API.** Same origin. Locally, requests go through the development server (/api and /sanctum only). In the emulated cloud and in prod, they go through the edge, where the web app and the API share one domain. A session cookie plus a CSRF token, accepted only from the stateful origins.
2. **Internet → edge → API Gateway.** Every request in the emulated cloud and in prod goes through the CloudFront distribution. It serves HTTPS only (TLS 1.2 at least with the prod domain), runs AWS WAF in prod and adds the web app's security headers from one file. It also adds the edge secret to every request to API Gateway. API Gateway's origin verifier refuses a request without the secret (401) or with a wrong value (403), before the request reaches the application. So the API responds only to what came through the edge, and the client's address is the entry the edge appended to X-Forwarded-For.
3. **Integrations → API.** Bearer API keys, each tied to one company; no cookies. The routes reserved for the web app session (users, keys, webhooks, certificates, DIAN settings, development tools) refuse API keys.
4. **API, workers and relay → MySQL and Redis.** The Compose internal network. Redis requires its password and publishes no port. In the emulated cloud, each function connects to MySQL as its database identity, over TLS. In prod, connections go from the private subnets to the isolated ones. There, only the functions' and the rotation functions' security groups reach the port, with TLS and the server's certificate verified.
5. **Workers → DIAN.** SOAP over HTTP to the simulator here. HTTPS and WS-Security in production (not built).
6. **Workers → webhook endpoints.** Outbound calls to URLs that tenants choose.
7. **Workers → mail server.** SMTP to the local mailbox here.
8. **API → simulator admin API and webhook receiver.** A token from the configuration; development tools only.
9. **Development tools on 127.0.0.1.** The local mailbox, the simulator and its webhook receiver, and the AWS emulator. No authentication beyond loopback.
10. **GitHub Actions → AWS (prod, never run).** The deployment workflow is dispatched by hand. It waits for a reviewer of the production environment, then assumes the deploy role with the token GitHub gives its job. The trust policy compares the audience and the subject (`repo:<owner>/<repository>:environment:production`) exactly.
11. **API, workers and relay → AWS services (emulated cloud).** The AWS SDK, through the adapters only. One managed policy per consumer and capability. The topic, queue and bucket policies require TLS, and only the topic may send to the queues. The emulator evaluates none of these policies.

## Threats and mitigations

| Threat | Mitigation | Tests |
| --- | --- | --- |
| Account takeover by guessing or spraying passwords | Five failures a minute per email and address, and twenty sign-ins a minute per address. A failed sign-in takes the same time whether or not the email exists. A 12-character minimum, and a new session id on sign-in. | AccountsTest |
| A stolen session outliving a password change | Changing or resetting the password ends every other session (Sanctum compares the password hash). Sign-out invalidates the session. | AccountsTest |
| Enumerating accounts and tenants | Sign-up returns the same message for a taken email or a taken NIT. A password reset request gets the same response for any address, and the link is sent from the queue. An old or used invitation link shows nothing about the person. | AccountsTest, InvitationLinksTest |
| Password reset and invitation links abused | Single use, valid for 60 minutes (a reset) or 7 days (an invitation). A resent invitation replaces the earlier link, even in a queued email. Limits per address. | AccountsTest, InvitationLinksTest |
| Reading or changing another company's data | The company middleware runs before route bindings. Every tenant model has a global scope that fails closed without a company. Another company's record returns 404. | TenantIsolationTest |
| A route left without authentication | Deny by default: every route except for a short public list returns 401 without credentials. | RouteAuthenticationTest |
| A role or a key doing more than allowed | The permission middleware on every route that changes data, owner rules in the team services, and key levels. The routes reserved for the web app session refuse API keys. | RolesTest, PublicApiTest |
| Cross-site request forgery and session riding | SameSite=Lax cookies, a CSRF token, and stateful origins checked by Origin and Referer. Behind the edge, the API reference shares the session's origin. So its third-party renderer runs only with the bytes its Subresource Integrity pins, under a policy that allows its inline scripts by hash. CORS is not offered for the CSRF cookie. | AccountsTest, EdgeTest, make cloud-e2e |
| Script injection | Vue escapes text, and no user content is inserted as HTML. JSON responses carry a Content-Security-Policy that allows nothing. Behind the edge, the web app has a strict policy: scripts and styles from its own origin only, inline ones by hash, never 'unsafe-inline' or 'unsafe-eval', no framing, no plugins, no base. Blade escapes every field of the PDF and the emails. | HostileInputTest, edge.test.ts, make cloud-e2e |
| Server-side request forgery through webhooks | Private, loopback, link-local, shared, reserved and multicast addresses are refused, IPv4 and IPv6. The check applies to the resolved address, and the call is pinned to it. No redirects. In production, https on port 443 only. Responses are read up to 64 KB. | PrivateTargetsTest, WebhookTargetsTest |
| XML external entities, entity expansion and zip bombs | No DTD is accepted anywhere (SafeXml in the backend, parseXml in the simulator, before xmllint and xmlsec1). xmlsec1 follows only same-document references. Zips are limited in size, entries, declared size and names. | SafeXmlTest, hostile-input.test.ts |
| SQL and email header injection | Bindings in every query, and $fillable in every model. Subjects are cleaned of line breaks, recipients are validated, and Symfony encodes the headers. | HostileInputTest |
| Secrets or personal data leaking through the database, logs or traces | Hashes and encrypted casts, as above. Secret parameters are marked #[SensitiveParameter]. No request headers are logged. Every response and log line carries X-Request-Id and the correlation id instead of request data. In the functions: structured lines with one schema's fields only, internal ids, a trace without arguments, and every text masked for keys, tokens, emails, identification numbers and documents (docs/observability.md). | SecretsInLogsTest, ObservabilityTest, make cloud-check |
| Errors revealing internals | Every error, inside and outside /api/v1, is problem+json without traces when APP_DEBUG is off. PHP's expose_php is off. | ErrorsAndHeadersTest |
| Uploads that are not what they claim | Certificates: 100 KB at most, .p12 or .pfx, opened with OpenSSL, with an RSA key that matches its certificate. The password never comes back. | HostileInputTest |
| A repeated or simultaneous request acting twice | The Idempotency-Key is committed with the effect in one transaction, and its row lock marks a running request. Outbox delivery is at least once, with idempotent consumers. Numbering is gap-free, under locks. Rule 90 and GetStatus before resending. | IdempotencyTest, IssueTest, ChainTest |
| Tampering with issued documents | The XAdES signature is verified independently, the stored XML keeps its SHA-256, and accepted documents never change. | ConformanceTest, ChainTest |
| Denial of service | Limits per key, user and address. Body and upload limits. Timeouts on every outbound call. Pruning of operational records. In prod, AWS WAF at the edge: the AWS IP reputation list and AWS managed rules. It also limits each address to 100 sign-in attempts and 3,000 requests in 5 minutes, counted on the address CloudFront sees. | AccountsTest, OperationsTest, edge.test.ts |
| A client that skips the edge, or forges its address | API Gateway accepts only requests that carry the edge secret (the origin verifier: a constant-time comparison, with its concurrency capped). Behind the edge, the rate limits count the entry the edge appended to X-Forwarded-For. API Gateway may append an entry for its peer, the source address it reports; once that entry is dropped, the edge's entry is the last one. The limits never count an address the client wrote in any header (X-Forwarded-For, CloudFront-Viewer-Address). Without the edge's entry, a request counts under the runtime's address, which makes the limits stricter. | EdgeTest, origin verifier tests, make cloud-check |
| An API route served as the web app, or the API's errors hidden | Every application path has a behavior of its own toward API Gateway (a test checks every route against paths.json). A CloudFront Function rewrites the web app's routes, on the default behavior only, never through custom error responses. So a 403 or 404 from the API stays the API's own problem response. | EdgeTest, edge.test.ts, make cloud-check |
| Clickjacking, sniffing, downgrade to HTTP | frame-ancestors 'none' and X-Frame-Options DENY, nosniff, HSTS for a year with subdomains on the web app and the API, and HTTPS only at the edge | ErrorsAndHeadersTest, edge.test.ts, make cloud-check |
| Development tools reaching real data | Stress, chaos, the checks and the demo seeder refuse to run outside the local and testing environments. The simulator refuses to start without its token. | ErrorsAndHeadersTest, hostile-input.test.ts |
| A forged or broken message in a queue | Queue policies let only the topic send (and the application, its own jobs). The consumer reads only events of the types its queue routes, with every field checked. Anything else fails on every receive, a second apart, until the redrive policy moves it to the dead-letter queue. The consumers stay idempotent. | CloudAdaptersTest, make cloud-check |
| A flaw in a function, exploited to change the database schema or privileges | Two identities. Only the console function holds the migrations identity. Every other function connects as the application identity, which may only read and write data, with TLS required. Each role reads only its own identity's secret. | DatabaseIdentitiesTest, CDK tests, make cloud-check |
| A database password that leaks | In prod, the identities rotate every 30 days (the application identity with alternating users). The database sits in isolated subnets without a route out, and only the functions' and the rotation functions' security groups reach it. It refuses connections without TLS. | CDK tests, DatabaseIdentitiesTest, make cloud-check |
| Cloud secrets in files or templates | Secrets Manager generates APP_KEY, which is never in a template. It is read at boot into the process environment, and kept up to 5 minutes in a file only the container's user can read. backend/.env.cloud holds names, not secrets. | CloudAdaptersTest, CDK tests, make cloud-check |
| A deployment by someone who should not deploy, or from a fork, a branch or a stolen key | No long-lived key: OpenID Connect, with credentials for an hour. The trust policy names exactly one environment of one repository, with required reviewers. One deployment at a time. The role holds only what the steps of scripts/deploy.sh need, on the project's resources. It changes no function, role or secret outside CloudFormation, and the pipeline never deploys its own stack. | delivery.test.ts, actionlint |
| A migration that breaks the release still running while the functions deploy | The console function gets the new image first, and runs the migrations before the other functions take the image. make migrations-check refuses a dropped or renamed column or table unless the migration names the release from which the change is safe. The database only goes forward. | MigrationSafetyTest, OperationCommandsTest |
| A vulnerable or incompatible dependency, or a committed secret | Lock files; the CI security job (high and critical advisories, GPL or AGPL in production dependencies, gitleaks over the history); Dependabot; pinned images | make security |

## Risks that remain

- No second factor: a password guessed slowly enough, or phished, is enough.
- Sign-up has no email verification, by decision. A refusal still reveals that the email or the NIT exists. One message for both cases, and ten attempts an hour per address, mitigate this.
- APP_KEY protects every encrypted secret, and it cannot be rotated without re-encrypting them. A copy of backend/.env together with the database exposes them.
- Tenants choose the webhook endpoints. A public endpoint that responds slowly, or with a lot of data, costs a worker up to 5 seconds per attempt.
- Behind the edge, the API reference runs a third-party renderer (Stoplight Elements, from unpkg.com) on the session's origin. Subresource Integrity pins its bytes, but a flaw in that version would run where the session lives. Its styles may be inline.
- No WS-Security toward the DIAN (not built).
- No Content-Security-Policy violation reports; make cloud-e2e catches violations in the browser.
- The functions' alarms reach the operators through the notifier and a chat whose address is a credential. The alarm on the notifier's failures also emails them.
- The prod stage's private network and managed database exist as code, validated but never deployed.
- In the emulated cloud, the functions encrypt their connections to MySQL without verifying its certificate: the Compose MySQL signs its own certificate, for another name. The local stack keeps fixed database credentials and one user.
- Each function has a role of its own, which attaches the managed policies the stacks create (one per consumer and capability). The emulated cloud proves the wiring, not those permissions: the emulator evaluates no IAM, resource or key policy, and applies no AWS WAF.
- The edge secret is visible to anyone who may read the distribution's configuration.
- A client's address rests on two behaviors. CloudFront appends its viewer's address to X-Forwarded-For, and API Gateway appends, if anything, the address of the peer it reports. A proxy added between the edge and API Gateway would make every client of an edge location share one address: stricter limits, not a forged address.
- The DIAN side is simulated: the real service's responses, failures and rules may differ.
- The deployment pipeline has never run: the deploy role is least privilege on paper, checked offline. CloudFormation deploys the CDK app's stacks with the CDK bootstrap's execution policy. That policy is AdministratorAccess unless the account owner provides a narrower one. So anyone who may approve a deployment may change anything those stacks may. The workflows' actions are pinned by major version, not by commit.
