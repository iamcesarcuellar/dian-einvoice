# Threat model

The platform as it runs here: a Laravel API, a Vue web app, MySQL, Redis, queue workers and an outbox relay, a local simulator of the DIAN and a local mailbox; in the emulated cloud ([infrastructure.md](infrastructure.md)), the application as Lambda functions behind API Gateway, fed by SQS and EventBridge Scheduler, each with a role of its own, with SNS, SQS, S3, SES, DynamoDB, KMS and Secrets Manager in a local emulator instead of Redis, the local disk and the local mailbox. Prod adds, as code, a private network and a managed database (task 3) and, in both stages, the edge (task 4): one CloudFront distribution in front of the web app and the API, with its security headers, a firewall in prod and an origin verifier on API Gateway; where a mitigation depends on them, this page says so. The known gaps are in [limitations.md](limitations.md).

## Assets

| Asset | Where it lives | How it is kept |
| --- | --- | --- |
| Signing keys of each company (PKCS#12 and its password) | key_store_entries (local), kms_key_store_entries (emulated cloud) | Locally encrypted with APP_KEY; in the emulated cloud AES-256-GCM with a data key per certificate that only the KMS key decrypts, bound to the company and the entry by the encryption context; never returned by the API |
| Software PIN and technical keys | dian_settings, number_templates | Encrypted with APP_KEY; only the last four characters of a technical key are shown |
| API keys | api_keys | SHA-256 of a 40-character random secret, compared in constant time; shown once |
| Webhook secrets | webhook_subscriptions | Encrypted with APP_KEY; shown once, on creation and rotation |
| Passwords and sessions | users, Redis | bcrypt; sessions in Redis behind an HttpOnly, SameSite=Lax cookie, Secure in production |
| Invitation and password reset links | team_invitations, password_reset_tokens | Only a hash of the token is stored; the token travels in the email |
| Invoices, notes, payments and customer data (names, identification numbers, emails, addresses) | MySQL, document storage (local disk, or the S3 bucket), events in the topic and the queues | Scoped to a company on every query; files served only by the API after authorization; the bucket is private, encrypted and versioned, and the topic and the queues are encrypted at rest |
| Integrity of numbering, documents and balances | MySQL | Row locks, gap-free numbering, signed XML with its SHA-256, accepted documents immutable |
| APP_KEY, Redis password, simulator admin token | backend/.env; in the emulated cloud APP_KEY and the credentials of the two identities of the database in Secrets Manager | Never committed; the Redis password and the token are random per checkout; the APP_KEY of the emulated cloud is generated by Secrets Manager and never written to a file of the repository |
| Secret of the edge | Secrets Manager; the configuration of the distribution, which sends it to API Gateway in X-Origin-Verify | Generated by Secrets Manager, never in a template or a file; compared in constant time by the origin verifier, whose role reads nothing else; the current and the previous versions are accepted, so it rotates without a cut (docs/infrastructure.md). Visible to whoever may read the configuration of the distribution |

## Actors

An anonymous visitor of the API or the web app; a signed-in user of another company; a member with a low role (viewer, member); the holder of an API key (read-only or read-write); the owner of a webhook endpoint; customer data typed into documents (names, notes); the DIAN web service, whose answers are trusted only after parsing; a compromised dependency or CDN.

## Trust boundaries

1. **Browser and web app → API.** Same origin: through the dev server (/api and /sanctum only) locally, through the edge in the emulated cloud and in prod, where the web app and the API share one domain. Session cookie plus CSRF token, accepted only from the stateful origins.
2. **Internet → edge → API Gateway.** Every request of the emulated cloud and of prod goes through the CloudFront distribution: HTTPS only (TLS 1.2 at least with the domain of prod), AWS WAF in prod, the security headers of the web app from one file. The distribution adds the secret of the edge to every request to API Gateway, whose origin verifier refuses a request without it (401) or with a wrong value (403) before the application, so the API answers only what came through the edge, and the address of the client is the entry the edge appended to X-Forwarded-For.
3. **Integrations → API.** Bearer API keys of one company; no cookies. Panel routes (users, keys, webhooks, certificates, DIAN settings, development tools) refuse keys.
4. **API, workers and relay → MySQL and Redis.** Internal network of compose; Redis needs its password and publishes no port. In the emulated cloud each function connects to MySQL as its identity of the database, over TLS; in prod, from the private subnets to the isolated ones, where only the security groups of the functions and of the rotation functions reach the port, with TLS and the certificate of the server verified.
5. **Workers → DIAN.** SOAP over HTTP to the simulator here; HTTPS and WS-Security in production (not built).
6. **Workers → webhook endpoints.** Outbound calls to URLs that tenants choose.
7. **Workers → mail server.** SMTP to the local mailbox here.
8. **API → simulator admin API and webhook receiver.** A token from configuration; development tools only.
9. **Development tools on 127.0.0.1.** The local mailbox, the simulator and its receiver, and the AWS emulator: no authentication beyond loopback.
10. **API, workers and relay → AWS services (emulated cloud).** The AWS SDK through the adapters only; one managed policy per consumer and capability, TLS required by the policies of the topic, the queues and the bucket, and only the topic may send to the queues. The emulator evaluates none of these policies.

## Threats and mitigations

| Threat | Mitigation | Tests |
| --- | --- | --- |
| Account takeover by guessing or spraying passwords | Five failures a minute per email and address, twenty sign-ins a minute per address, failed sign-ins take the same time whether or not the email exists, 12-character minimum, a new session id on sign-in | AccountsTest |
| A stolen session outliving a password change | Changing or resetting the password ends every other session (Sanctum compares the password hash); sign-out invalidates the session | AccountsTest |
| Enumerating accounts and tenants | Sign-up answers one message for a taken email or NIT; the reset link answers the same for any address and is sent from the queue; an old or used invitation link shows nothing about the person | AccountsTest, InvitationLinksTest |
| Password reset and invitation links abused | Single use, 60 minutes for a reset and 7 days for an invitation, a resent invitation replaces the earlier link even in a queued email, limits per address | AccountsTest, InvitationLinksTest |
| Reading or changing another company's data | The company middleware runs before route bindings; every tenant model has a global scope that fails closed without a company; a record of another company answers 404 | TenantIsolationTest |
| A route left without authentication | Deny by default: every route but a short public list answers 401 without credentials | RouteAuthenticationTest |
| A role or a key doing more than allowed | permission middleware on every route that changes data, owner rules in the team services, key levels, panel routes refuse keys | RolesTest, PublicApiTest |
| Cross-site request forgery and session riding | SameSite=Lax cookies, CSRF token, stateful origins checked by Origin and Referer; behind the edge the API reference shares the origin of the session, so its third-party renderer runs only with the bytes its Subresource Integrity pins, under a policy that allows its inline scripts by hash; CORS is not offered for the CSRF cookie | AccountsTest, EdgeTest, make cloud-e2e |
| Script injection | Vue escapes text and no user content is inserted as HTML; JSON answers carry a Content-Security-Policy that allows nothing; behind the edge the web app has a strict policy: scripts and styles of its own origin only, inline ones by hash, never 'unsafe-inline' or 'unsafe-eval', no framing, no plugins, no base; Blade escapes every field of the PDF and the emails | HostileInputTest, edge.test.ts, make cloud-e2e |
| Server-side request forgery through webhooks | Private, loopback, link-local, shared, reserved and multicast addresses refused, IPv4 and IPv6, on the resolved address, which the call is pinned to; no redirects; https on port 443 only in production; answers read up to 64 KB | PrivateTargetsTest, WebhookTargetsTest |
| XML external entities, entity expansion and zip bombs | No DTD is accepted anywhere (SafeXml in the backend, parseXml in the simulator, before xmllint and xmlsec1); xmlsec1 follows only same-document references; zips limited in size, entries, declared size and names | SafeXmlTest, hostile-input.test.ts |
| SQL and email header injection | Bindings in every query, $fillable in every model; subjects cleaned of line breaks, recipients validated, Symfony encodes headers | HostileInputTest |
| Secrets leaking through the database, logs or traces | Hashes and encrypted casts as above; secret parameters marked #[SensitiveParameter]; no request headers logged; X-Request-Id in every answer and log line instead of request data | SecretsInLogsTest, ErrorsAndHeadersTest |
| Errors revealing internals | Every error, inside and outside /api/v1, is problem+json without traces when APP_DEBUG is off; expose_php off | ErrorsAndHeadersTest |
| Uploads that are not what they claim | Certificates: 100 KB, .p12 or .pfx, opened with OpenSSL, RSA key matching its certificate; the password never comes back | HostileInputTest |
| A repeated or simultaneous request acting twice | Idempotency-Key committed with the effect in one transaction, its row lock marking a running request; outbox delivery at least once with idempotent consumers; gap-free numbering under locks; rule 90 and GetStatus before resending | IdempotencyTest, IssueTest, ChainTest |
| Tampering with issued documents | XAdES signature verified independently, SHA-256 of the stored XML, accepted documents never change | ConformanceTest, ChainTest |
| Denial of service | Limits per key, user and address; body and upload limits; timeouts on every outbound call; pruning of operational records; in prod AWS WAF at the edge: the IP reputation list of AWS, its managed rules, 100 sign-in attempts and 3,000 requests per address in 5 minutes, counted on the address CloudFront sees | AccountsTest, OperationsTest, edge.test.ts |
| A client that skips the edge, or forges its address | API Gateway answers only requests that carry the secret of the edge (origin verifier, constant-time comparison, its concurrency capped); behind the edge the rate limits count the entry the edge appended to X-Forwarded-For, the last one once an entry API Gateway appended for its peer (the source address it reports) is dropped, never an address the client wrote in any header (X-Forwarded-For, CloudFront-Viewer-Address); without it a request counts as the runtime, which makes limits stricter | EdgeTest, origin verifier tests, make cloud-check |
| A route of the API served as the web app, or the errors of the API hidden | Every path of the application is a behaviour of its own toward API Gateway (a test checks every route against paths.json); the routes of the web app are rewritten by a CloudFront Function on the default behaviour only, never by custom error responses, so a 403 or 404 of the API stays a problem of the API | EdgeTest, edge.test.ts, make cloud-check |
| Clickjacking, sniffing, downgrade to HTTP | frame-ancestors 'none' and X-Frame-Options DENY, nosniff, HSTS for a year with subdomains on the web app and the API, HTTPS only at the edge | ErrorsAndHeadersTest, edge.test.ts, make cloud-check |
| Development tools reaching real data | Stress, chaos, the checks and the demo seeder refuse to run outside local and testing; the simulator refuses to start without its token | ErrorsAndHeadersTest, hostile-input.test.ts |
| A forged or broken message in a queue | Queue policies let only the topic send (and the application its own jobs); the consumer reads only events of the types its queue routes, with every field checked, and sends anything else to the dead-letter queue after the receives of the redrive policy; the consumers stay idempotent | CloudAdaptersTest, make cloud-check |
| A flaw in a function used to change the schema or the privileges of the database | Two identities: only the console function holds the migrations identity; every other function connects as the application identity, which may only read and write data, TLS required; each role reads only the secret of its own identity | DatabaseIdentitiesTest, CDK tests, make cloud-check |
| A database password that leaks | The identities rotate every 30 days in prod (the application one with alternating users), the database is reachable only from the security groups of the functions and of the rotation functions, in isolated subnets without a route out, and refuses connections without TLS | CDK tests, DatabaseIdentitiesTest, make cloud-check |
| Secrets of the cloud in files or templates | APP_KEY generated by Secrets Manager, never in a template; read at boot into the environment of the process, kept up to 5 minutes in a file only the user of the container reads; backend/.env.cloud holds names, not secrets | CloudAdaptersTest, CDK tests, make cloud-check |
| A vulnerable or incompatible dependency, a committed secret | Lock files, the security job of CI (high and critical advisories, GPL or AGPL in production dependencies, gitleaks over the history), Dependabot, pinned images | make security |

## Risks that remain

- No second factor: a password guessed or phished slowly enough is enough.
- Sign-up has no email verification (a decision): a refusal still tells that the email or the NIT exists, mitigated by one message for both and ten attempts an hour per address.
- APP_KEY protects every encrypted secret and cannot be rotated without re-encrypting them; a copy of backend/.env and the database together exposes them.
- Webhook endpoints are chosen by tenants: a public endpoint that answers slowly or with a lot of data costs a worker up to 5 seconds per attempt.
- Behind the edge the API reference runs a third-party renderer (Stoplight Elements, from unpkg.com) on the origin of the session: Subresource Integrity pins its bytes, but a flaw in that version would run where the session lives; its styles may be inline.
- No WS-Security toward the DIAN (not built); until task 5, no metrics or alerts, and no reports of violations of the Content-Security-Policy (make cloud-e2e catches them in the browser). The private network and the managed database of prod exist as code, validated but never deployed. In the emulated cloud the functions encrypt their connections to MySQL without verifying its certificate (the MySQL of compose signs its own, for another name), and the local stack keeps fixed database credentials and one user. The roles of the functions attach the managed policies of task 1, one role per function (task 2).
- The emulated cloud proves the wiring, not the permissions: the emulator evaluates no IAM, resource or key policy, and applies no AWS WAF. The secret of the edge is visible to whoever may read the configuration of the distribution. The address of a client rests on CloudFront appending the address of its viewer to X-Forwarded-For, and on API Gateway appending, if anything, the address of the peer it reports: a proxy added between the edge and API Gateway would make every client of an edge location share one address (stricter limits, not a forged address).
- The DIAN side is simulated: answers, failures and rules of the real service may differ.
