Esta página modela la plataforma tal como corre aquí:

- **El stack local**: una API en Laravel, una aplicación web en Vue, MySQL, Redis, los workers de la cola y un relay del outbox, el simulador de la DIAN y un buzón local.
- **La nube emulada** ([infrastructure.md](infrastructure.md)): la aplicación corre como funciones Lambda detrás de API Gateway, alimentadas por SQS y EventBridge Scheduler, cada función con su propio rol. SNS, SQS, S3, SES, DynamoDB, KMS y Secrets Manager corren en un emulador local, en lugar de Redis, el disco local y el buzón local.

La etapa de producción agrega, como código, una red privada y una base de datos administrada. Las dos etapas tienen además el borde: una distribución de CloudFront delante de la aplicación web y de la API. El borde trae sus cabeceras de seguridad, un firewall en producción y un verificador de origen en API Gateway. Cuando una mitigación depende de estas piezas, esta página lo dice. [limitations.md](limitations.md) lista los vacíos conocidos.

## Actores

- Un visitante anónimo de la API o de la aplicación web
- Un usuario de otra empresa, con su sesión iniciada
- Un miembro con un rol bajo (lector, miembro)
- El portador de una llave de API (de solo lectura o de lectura y escritura)
- El dueño de un endpoint de webhooks
- Los datos de los clientes que se escriben en los documentos (nombres, observaciones)
- El servicio web de la DIAN, en cuyas respuestas solo se confía después de parsearlas
- Una dependencia o un CDN comprometidos

## Fronteras de confianza

1. **Navegador y aplicación web → API.** El mismo origen. En local, las peticiones pasan por el servidor de desarrollo (solo /api y /sanctum). En la nube emulada y en producción, pasan por el borde, donde la aplicación web y la API comparten un dominio. Una cookie de sesión más un token CSRF, que solo se aceptan desde los orígenes con estado (stateful).
2. **Internet → borde → API Gateway.** En la nube emulada y en producción, cada petición pasa por la distribución de CloudFront. Esta sirve solo HTTPS (como mínimo TLS 1.2 con el dominio de producción), corre AWS WAF en producción y agrega las cabeceras de seguridad de la aplicación web, que salen de un solo archivo. También agrega el secreto del borde a cada petición hacia API Gateway. El verificador de origen de API Gateway rechaza una petición sin el secreto (401) o con un valor equivocado (403), antes de que llegue a la aplicación. Así, la API solo responde a lo que llegó por el borde, y la dirección del cliente es la entrada que el borde agregó a X-Forwarded-For.
3. **Integraciones → API.** Llaves de API enviadas como Bearer, cada una atada a una empresa; sin cookies. Las rutas reservadas para la sesión de la aplicación web (usuarios, llaves, webhooks, certificados, configuración DIAN, herramientas de desarrollo) rechazan las llaves de API.
4. **API, workers y relay → MySQL y Redis.** La red interna de Compose. Redis exige su contraseña y no publica ningún puerto. En la nube emulada, cada función se conecta a MySQL con su identidad de la base de datos, sobre TLS. En producción, las conexiones van de las subredes privadas a las aisladas. Allí, solo los grupos de seguridad de las funciones y de las funciones de rotación llegan al puerto, con TLS y con el certificado del servidor verificado.
5. **Workers → DIAN.** Aquí, SOAP sobre HTTP hacia el simulador. HTTPS y WS-Security en producción (sin construir).
6. **Workers → endpoints de webhooks.** Llamadas salientes a URL que eligen las empresas.
7. **Workers → servidor de correo.** Aquí, SMTP hacia el buzón local.
8. **API → API de administración del simulador y receptor de webhooks.** Un token de la configuración; solo herramientas de desarrollo.
9. **Herramientas de desarrollo en 127.0.0.1.** El buzón local, el simulador y su receptor de webhooks, y el emulador de AWS. Sin más autenticación que el loopback.
10. **GitHub Actions → AWS (producción, nunca ha corrido).** El flujo de despliegue se lanza a mano. Espera a un revisor del entorno de producción y luego asume el rol de despliegue con el token que GitHub le da a su trabajo. La política de confianza compara exactamente la audiencia y el sujeto (`repo:<owner>/<repository>:environment:production`).
11. **API, workers y relay → servicios de AWS (nube emulada).** El SDK de AWS, solo a través de los adaptadores. Una política administrada por consumidor y capacidad. Las políticas del tema, de las colas y del bucket exigen TLS, y solo el tema puede enviar a las colas. El emulador no evalúa ninguna de estas políticas.

## Amenazas y mitigaciones

| Amenaza | Mitigación | Pruebas |
| --- | --- | --- |
| Robo de cuentas adivinando contraseñas, o probando unas pocas en muchas cuentas | Cinco intentos fallidos por minuto por correo y dirección, y veinte inicios de sesión por minuto por dirección. Un inicio de sesión fallido tarda lo mismo, exista o no el correo. Un mínimo de 12 caracteres, y un id de sesión nuevo al iniciar sesión. | AccountsTest |
| Una sesión robada que sobrevive a un cambio de contraseña | Cambiar o restablecer la contraseña cierra todas las demás sesiones (Sanctum compara el hash de la contraseña). Cerrar sesión invalida la sesión. | AccountsTest |
| Enumerar cuentas y empresas | Crear una cuenta devuelve el mismo mensaje tanto si el correo ya está en uso como si lo está el NIT. Una petición de restablecimiento de contraseña recibe la misma respuesta para cualquier dirección de correo, y el enlace sale desde la cola. Un enlace de invitación viejo o ya usado no muestra nada de la persona. | AccountsTest, InvitationLinksTest |
| Abuso de los enlaces de restablecimiento de contraseña y de invitación | De un solo uso, válidos por 60 minutos (un restablecimiento) o 7 días (una invitación). Una invitación reenviada reemplaza el enlace anterior, incluso en un correo que sigue en la cola. Límites por dirección. | AccountsTest, InvitationLinksTest |
| Leer o cambiar los datos de otra empresa | El middleware de la empresa corre antes de que se resuelvan los modelos de la ruta. Cada modelo multiempresa tiene un scope global que falla en modo cerrado si no hay empresa. Un recurso de otra empresa devuelve 404. | TenantIsolationTest |
| Una ruta que quedó sin autenticación | Denegar por defecto: cada ruta, salvo una lista pública corta, devuelve 401 sin credenciales. | RouteAuthenticationTest |
| Un rol o una llave que hace más de lo permitido | El middleware de permisos en cada ruta que cambia datos, las reglas del propietario en los servicios del equipo y los niveles de las llaves. Las rutas reservadas para la sesión de la aplicación web rechazan las llaves de API. | RolesTest, PublicApiTest |
| Falsificación de peticiones entre sitios y session riding | Cookies SameSite=Lax, un token CSRF y orígenes con estado revisados por Origin y Referer. Detrás del borde, la referencia de la API comparte el origen de la sesión. Por eso su renderizador de terceros solo corre con los bytes que fija su Subresource Integrity, bajo una política que permite su JavaScript en línea por hash. No se ofrece CORS para la cookie CSRF. | AccountsTest, EdgeTest, make cloud-e2e |
| Inyección de JavaScript | Vue escapa el texto, y ningún contenido de los usuarios se inserta como HTML. Las respuestas JSON llevan una Content-Security-Policy que no permite nada. Detrás del borde, la aplicación web tiene una política estricta: JavaScript y estilos solo de su propio origen, los que van en línea por su hash, nunca 'unsafe-inline' ni 'unsafe-eval', sin marcos, sin plugins, sin base. Blade escapa cada campo del PDF y de los correos. | HostileInputTest, edge.test.ts, make cloud-e2e |
| Falsificación de peticiones del lado del servidor a través de los webhooks | Se rechazan las direcciones privadas, de loopback, link-local, compartidas, reservadas y multicast, en IPv4 y en IPv6. La revisión se aplica a la dirección resuelta, y la llamada queda fijada a ella. Sin redirecciones. En producción, solo https en el puerto 443. Las respuestas se leen hasta 64 KB. | PrivateTargetsTest, WebhookTargetsTest |
| Entidades externas de XML, expansión de entidades y bombas zip | No se acepta ningún DTD en ninguna parte (SafeXml en el backend, parseXml en el simulador, antes de xmllint y xmlsec1). xmlsec1 solo sigue referencias dentro del mismo documento. Los zip tienen límites de tamaño, de entradas, de tamaño declarado y de nombres. | SafeXmlTest, hostile-input.test.ts |
| Inyección de SQL y de cabeceras de correo | Bindings en cada consulta, y $fillable en cada modelo. A los asuntos se les quitan los saltos de línea, los destinatarios se validan y Symfony codifica las cabeceras. | HostileInputTest |
| Secretos o datos personales que se filtran por la base de datos, los registros o las trazas | Hashes y casts cifrados, como arriba. Los parámetros secretos llevan #[SensitiveParameter]. Ninguna cabecera de las peticiones va a los registros. Cada respuesta y cada línea de registro lleva X-Request-Id y el id de correlación en lugar de datos de la petición. En las funciones: líneas estructuradas solo con los campos de un esquema, ids internos, una traza sin argumentos, y en cada texto se enmascaran llaves, tokens, correos, números de identificación y documentos (docs/es/observability.md). | SecretsInLogsTest, ObservabilityTest, make cloud-check |
| Errores que revelan detalles internos | Todo error, dentro y fuera de /api/v1, es problem+json sin trazas cuando APP_DEBUG está apagado. El expose_php de PHP está apagado. | ErrorsAndHeadersTest |
| Archivos subidos que no son lo que dicen ser | Certificados: 100 KB como máximo, .p12 o .pfx, abiertos con OpenSSL, con una clave RSA que corresponda a su certificado. La contraseña nunca se devuelve. | HostileInputTest |
| Una petición repetida o simultánea que actúa dos veces | La Idempotency-Key se guarda junto con su efecto en una sola transacción, y su bloqueo de fila marca una petición en curso. El outbox entrega al menos una vez, con consumidores idempotentes. Numeración sin saltos, con bloqueos. La regla 90 y GetStatus antes de reenviar. | IdempotencyTest, IssueTest, ChainTest |
| Alterar los documentos emitidos | La firma XAdES se verifica de forma independiente, el XML guardado conserva su SHA-256 y los documentos aceptados nunca cambian. | ConformanceTest, ChainTest |
| Denegación de servicio | Límites por llave, por usuario y por dirección. Límites al cuerpo de las peticiones y a los archivos subidos. Tiempos de espera en cada llamada saliente. Depuración de los datos operativos. En producción, AWS WAF en el borde: la lista de reputación de IP de AWS y las reglas administradas de AWS. Además, limita cada dirección a 100 intentos de inicio de sesión y 3.000 peticiones en 5 minutos, contados sobre la dirección que ve CloudFront. | AccountsTest, OperationsTest, edge.test.ts |
| Un cliente que se salta el borde, o que falsifica su dirección | API Gateway solo acepta las peticiones que llevan el secreto del borde (el verificador de origen: una comparación en tiempo constante, con su concurrencia limitada). Detrás del borde, los límites de peticiones cuentan la entrada que el borde agregó a X-Forwarded-For. API Gateway puede agregar una entrada para el extremo de la conexión, la dirección de origen que reporta; una vez descartada esa entrada, la del borde es la última. Los límites nunca cuentan una dirección que el cliente escriba en una cabecera, cualquiera que sea (X-Forwarded-For, CloudFront-Viewer-Address). Sin la entrada del borde, una petición cuenta bajo la dirección del runtime, lo que vuelve más estrictos los límites. | EdgeTest, pruebas del verificador de origen, make cloud-check |
| Una ruta de la API servida como la aplicación web, o los errores de la API ocultos | Cada ruta de la aplicación tiene su propio comportamiento hacia API Gateway (una prueba revisa cada ruta contra paths.json). Una CloudFront Function reescribe las rutas de la aplicación web, solo en el comportamiento por defecto, nunca con respuestas de error personalizadas. Así, un 403 o un 404 de la API sigue siendo la respuesta problem+json de la propia API. | EdgeTest, edge.test.ts, make cloud-check |
| Clickjacking, sniffing del tipo de contenido, degradación a HTTP | frame-ancestors 'none' y X-Frame-Options DENY, nosniff, HSTS por un año con subdominios en la aplicación web y en la API, y solo HTTPS en el borde | ErrorsAndHeadersTest, edge.test.ts, make cloud-check |
| Herramientas de desarrollo que llegan a datos reales | Stress, chaos, las revisiones y el seeder de la demo se niegan a correr fuera de los entornos local y testing. El simulador se niega a arrancar sin su token. | ErrorsAndHeadersTest, hostile-input.test.ts |
| Un mensaje falsificado o dañado en una cola | Las políticas de las colas solo dejan enviar al tema (y a la aplicación, sus propios trabajos). El consumidor solo lee eventos de los tipos que enruta su cola, con cada campo revisado. Cualquier otro mensaje falla en cada recepción, con un segundo de diferencia, hasta que la política de redrive lo mueve a la cola de mensajes fallidos. Los consumidores siguen siendo idempotentes. | CloudAdaptersTest, make cloud-check |
| Una falla en una función, aprovechada para cambiar el esquema o los privilegios de la base de datos | Dos identidades. Solo la función de consola tiene la identidad de migraciones. Todas las demás funciones se conectan con la identidad de la aplicación, que solo puede leer y escribir datos, con TLS obligatorio. Cada rol lee solo el secreto de su propia identidad. | DatabaseIdentitiesTest, pruebas de CDK, make cloud-check |
| Una contraseña de la base de datos que se filtra | En producción, las identidades rotan cada 30 días (la identidad de la aplicación, con usuarios alternos). La base de datos está en subredes aisladas sin ruta de salida, y solo llegan a ella los grupos de seguridad de las funciones y de las funciones de rotación. Rechaza las conexiones sin TLS. | pruebas de CDK, DatabaseIdentitiesTest, make cloud-check |
| Secretos de la nube en archivos o plantillas | Secrets Manager genera APP_KEY, que nunca está en una plantilla. Al arrancar, se carga en el entorno del proceso, y se guarda hasta 5 minutos en un archivo que solo puede leer el usuario del contenedor. backend/.env.cloud tiene nombres, no secretos. | CloudAdaptersTest, pruebas de CDK, make cloud-check |
| Un despliegue de alguien que no debería desplegar, o desde un fork, una rama o una llave robada | Ninguna llave de larga duración: OpenID Connect, con credenciales por una hora. La política de confianza nombra exactamente un entorno de un repositorio, con revisores obligatorios. Un despliegue a la vez. El rol solo tiene lo que necesitan los pasos de scripts/deploy.sh, sobre los recursos del proyecto. No cambia ninguna función, rol ni secreto por fuera de CloudFormation, y el pipeline nunca despliega su propio stack. | delivery.test.ts, actionlint |
| Una migración que rompe la versión que sigue corriendo mientras se despliegan las funciones | La función de consola recibe primero la imagen nueva, y corre las migraciones antes de que las demás funciones tomen la imagen. make migrations-check rechaza una columna o una tabla borrada o renombrada, salvo que la migración nombre la versión desde la cual el cambio es seguro. La base de datos solo avanza. | MigrationSafetyTest, OperationCommandsTest |
| Una dependencia vulnerable o incompatible, o un secreto en un commit | Archivos de bloqueo; el trabajo de seguridad de la integración continua (avisos altos y críticos, GPL o AGPL en las dependencias de producción, gitleaks sobre el historial); Dependabot; imágenes fijadas | make security |

## Riesgos que quedan

- Sin segundo factor: basta una contraseña adivinada con suficiente lentitud, o robada con phishing.
- Crear una cuenta no verifica el correo, a propósito. Un rechazo sigue revelando que el correo o el NIT existen. Lo mitigan un solo mensaje para los dos casos y diez intentos por hora por dirección.
- APP_KEY protege cada secreto cifrado, y no se puede rotar sin volver a cifrarlos. Una copia de backend/.env junto con la base de datos los expone.
- Las empresas eligen los endpoints de los webhooks. Un endpoint público que responde despacio, o con muchos datos, le cuesta a un worker hasta 5 segundos por intento.
- Detrás del borde, la referencia de la API corre un renderizador de terceros (Stoplight Elements, desde unpkg.com) en el origen de la sesión. Subresource Integrity fija sus bytes, pero una falla en esa versión correría donde vive la sesión. Sus estilos pueden ir en línea.
- Sin WS-Security hacia la DIAN (sin construir).
- Sin reportes de violaciones de la Content-Security-Policy; make cloud-e2e detecta las violaciones en el navegador.
- Las alarmas de las funciones llegan a los operadores por el notificador y por un chat cuya dirección es una credencial. La alarma sobre las fallas del notificador también les llega por correo.
- La red privada y la base de datos administrada de la etapa de producción existen como código, validadas pero nunca desplegadas.
- En la nube emulada, las funciones cifran sus conexiones a MySQL sin verificar su certificado: el MySQL de Compose firma su propio certificado, para otro nombre. El stack local mantiene credenciales fijas para la base de datos y un solo usuario.
- Cada función tiene su propio rol, que adjunta las políticas administradas que crean los stacks (una por consumidor y capacidad). La nube emulada prueba el cableado, no esos permisos: el emulador no evalúa ninguna política de IAM, de recursos ni de llaves, y no aplica AWS WAF.
- Cualquiera que pueda leer la configuración de la distribución ve el secreto del borde.
- La dirección de un cliente depende de dos comportamientos. CloudFront agrega la dirección de su visitante a X-Forwarded-For, y API Gateway agrega, si agrega algo, la dirección del extremo de la conexión, tal como la reporta. Un proxy que se agregara entre el borde y API Gateway haría que todos los clientes de una ubicación de borde compartieran una dirección: límites más estrictos, no una dirección falsificada.
- El lado de la DIAN es simulado: las respuestas, las fallas y las reglas del servicio real pueden ser distintas.
- El pipeline de despliegue nunca ha corrido: el rol de despliegue es de mínimo privilegio en el papel, revisado sin conexión. CloudFormation despliega los stacks de la app de CDK con la política de ejecución del bootstrap de CDK. Esa política es AdministratorAccess, salvo que el dueño de la cuenta defina una más restringida. Así que cualquiera que pueda aprobar un despliegue puede cambiar todo lo que esos stacks pueden cambiar. Las acciones de los flujos de trabajo se fijan por versión mayor, no por commit.
